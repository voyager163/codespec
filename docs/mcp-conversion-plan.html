Conversion Plan · PowerCodex

CLI → MCP Server

A phased plan to expose PowerCodex's lifecycle engine, project scaffolder, and planning tools as a Model Context Protocol (MCP) server — letting any MCP-compatible host (Claude Desktop, VS Code, Cursor, etc.) drive Power Apps development natively.

● MCP SDK 1.x ● Node.js ≥ 20.19 ● Zero new dependencies on core logic
1 Why convert to MCP?
Host-native UX

Claude Desktop, VS Code, and Cursor can call PowerCodex tools directly from the chat UI — no terminal needed.

AI-driven loops

Claude can read lifecycle state as a resource, call tools to advance phases, and receive streaming progress — fully agentic.

Zero logic rewrite

The existing lifecycle engine, plan generator, story/digest system, and compliance meter stay unchanged — MCP is a thin transport layer on top.

2 Capability → MCP primitive mapping

MCP has three primitives: Tools (model-invokable actions), Resources (readable data), and Prompts (templated instructions).

5 Implementation phases
Phase 1 — Foundation
~2–3 hours · Get a working MCP server that Claude Desktop can connect to
  • Add @modelcontextprotocol/sdk to package.json (the official Anthropic SDK)
  • Create bin/powercodex-mcp.mjs — starts stdio server, imports src/mcp/server.mjs
  • Register the server in Claude Desktop's claude_desktop_config.json under mcpServers
  • Implement one smoke-test tool: ping → returns { ok: true, version }
  • Verify the tool appears and calls succeed in Claude Desktop
Phase 2 — Scaffold & Import tools
~3–4 hours · The two most standalone capabilities
  • Implement scaffold_project(name, targetDir, options) — child-process create-powercodex.js, stream output back as progress notifications
  • Implement import_project(projectDir) — calls import.js analyze path, returns digest
  • Add Zod input schemas (validated by MCP SDK automatically)
  • Write a test: ask Claude "scaffold a new app called TestApp in /tmp" and verify folder exists
Phase 3 — Lifecycle tools
~4–6 hours · Core value — AI-driven loop control
  • Implement start_lifecycle_loop(goal, options) — spawns loop.js, stores run ID in memory map
  • Implement control_lifecycle(runId, action) — posts to loop's event emitter (approve/pause/stop)
  • Implement powercodex://lifecycle/state resource — reads loop state store, returns JSON
  • Handle streaming: emit MCP progress notifications as loop advances stages
  • Implement get_compliance(projectDir) — calls compliance.js
Phase 4 — Planning & Story tools
~2–3 hours · Content-generation tools
  • Implement generate_plan(goal, projectDir) — calls planner.js, registers in plan registry, returns HTML
  • Implement generate_stories(projectDir) — calls stories.js, returns structured array
  • Implement propose_mvp(goal, projectDir) — calls digest → planner pipeline
  • Implement powercodex://plans/{id} resource template — reads plan registry JSON
Phase 5 — Prompts & Lessons
~1–2 hours · Surface OPSX prompts as MCP prompts
  • Implement opsx.mjs — reads all .github/prompts/*.md files from the connected project dir, registers each as an MCP prompt
  • Implement log_lesson(lesson, context) tool — appends to Learning_Experience/
  • Implement powercodex://lessons resource — calls workspace.js aggregate
  • Add list_edge_profiles() tool for real-run setup
Phase 6 — Polish & publish
~2–3 hours · Package for distribution
  • Add "powercodex-mcp": "bin/powercodex-mcp.mjs" to package.json#bin
  • Write claude_desktop_config.json snippet in README — one-line install
  • Run self-test against MCP inspector (npx @modelcontextprotocol/inspector)
  • Bump to v0.2.0 and publish to npm
6 Code skeleton

bin/powercodex-mcp.mjs — entry point

#!/usr/bin/env node
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';
import { createServer } from '../src/mcp/server.mjs';

const server = createServer();
const transport = new StdioServerTransport();
await server.connect(transport);

src/mcp/server.mjs — server factory

import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { scaffoldTool }   from './tools/scaffold.mjs';
import { lifecycleTools } from './tools/lifecycle.mjs';
import { plannerTool }    from './tools/planner.mjs';
import { stateResource }  from './resources/state.mjs';
import { opsx Prompts }   from './prompts/opsx.mjs';

export function createServer() {
  const server = new McpServer({
    name: 'powercodex',
    version: '0.2.0',
  });

  // Register tools
  scaffoldTool(server);
  lifecycleTools(server);
  plannerTool(server);

  // Register resources
  stateResource(server);

  // Register prompts
  opsxPrompts(server);

  return server;
}

src/mcp/tools/scaffold.mjs — example tool

import { z } from 'zod';
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';
import { fileURLToPath } from 'node:url';
import path from 'node:path';

const execAsync = promisify(execFile);
const BIN = path.resolve(fileURLToPath(import.meta.url), '../../../../bin/create-powercodex.js');

export function scaffoldTool(server) {
  server.tool(
    'scaffold_project',
    {
      name:      z.string().describe('App name (kebab-case)'),
      targetDir: z.string().describe('Absolute path to create the project in'),
      skipInstall: z.boolean().optional().default(false),
      skipGit:     z.boolean().optional().default(false),
    },
    async ({ name, targetDir, skipInstall, skipGit }) => {
      const args = [name];
      if (skipInstall) args.push('--skip-install');
      if (skipGit)     args.push('--skip-git');
      const { stdout } = await execAsync('node', [BIN, ...args], { cwd: targetDir });
      return { content: [{ type: 'text', text: stdout }] };
    }
  );
}

7 Key decisions to make
Transport: stdio vs SSE?

Stdio — simplest, zero network config, works in Claude Desktop. Recommended for Phase 1–5.

SSE (HTTP) — needed if the lifecycle dashboard server and MCP server share a port. Use for Phase 6+ if you want browser + MCP in one process.

Lifecycle state: in-process vs file?

The existing loop.js holds state in memory. The MCP server is a separate process.

Options: (a) Write state to a JSON file (simplest), (b) MCP server spawns loop as a child and manages it, (c) use SSE so they share a process.

Project dir: global vs per-call?

Pass projectDir as a parameter on every tool call (flexible, multi-project) or configure once at server startup via an env var (simpler).

Recommendation: env var as default, per-call override.

Publish separately or same package?

Keep in same @voyager163/powercodex package — users get MCP for free with npm i -g @voyager163/powercodex.

Or publish @voyager163/powercodex-mcp separately — cleaner dep tree, opt-in only.
