The whole idea in one paragraph

Wrap the existing engine in a thin MCP server. Don't rebuild it — expose it.

PowerCodex already has the hard parts: the OpenSpec HTML planning workflow, the two managed-browser engines (build & self-healing test), the consent gate (Approved_rights/), the live dashboard, and the learning log. The MCP route adds one new surface — a standards-compliant MCP server that publishes those capabilities as Tools (verbs the AI can call), Resources (artifacts the AI can read), and Prompts (the /opsx workflows as reusable templates). Any MCP-capable client connects, and the user steers the entire lifecycle in their own chat — while the human-in-the-loop gates are enforced server-side through MCP elicitation, so "bring your own AI" never means "bypass the approval."

◆Tools

The 7 lifecycle stages become callable verbs: plan_change, build_assets, run_app, test_app, self_heal, observe. The AI orchestrates; the server does the work.

▤Resources

The spec HTML, the dashboard state, the task contracts, and the Learning_Experience/ log are read-only context the AI can pull on demand.

⌘Prompts

The OpenSpec slash-commands (opsx:propose, opsx:apply…) ship as MCP prompt templates — discoverable in any client's prompt picker.

Same engine, new front door

The MCP server is an adapter, not a fork. It calls the exact same skills, engines, and gates the editor build uses. A bug fixed in the loop is fixed for both surfaces — there is one source of truth.

Why an MCP server at all

From "PowerCodex's editor" to "your AI, anywhere"

The Model Context Protocol is the emerging open standard (JSON-RPC 2.0 over stdio or streamable HTTP) for connecting AI assistants to external systems. Shipping PowerCodex as an MCP server means the user no longer has to adopt a specific editor or chat app — they bring the assistant they already trust, and PowerCodex becomes one of its tools.

🔌Bring your own AI

Claude Desktop, Claude Code, Cursor, Cline, Windsurf, VS Code Copilot (MCP), ChatGPT desktop, or a bespoke Agent SDK app — anything that speaks MCP can drive the loop.

🧩Composable

PowerCodex sits alongside the user's other MCP servers (GitHub, Playwright, filesystem, Jira). Their AI can weave a Power App build into a larger workflow.

🛡️Gates travel with it

The consent gate isn't a UI nicety — it's enforced in the server via elicitation. No client can call build or push without a human approving the elicited request.

📈One engine to maintain

Editor users and MCP users share the same engines, dashboard, and learning log. No second codebase, no drift.

What MCP does not change

The Power Platform mechanics are identical: managed Edge browser in the maker portal for builds, power-apps push vs npm run dev for runs, e2e tests against the approved MVP, opsx self-heal on failure. MCP only changes who issues the instructions and how approvals are requested.

The shape of it

Three layers: the client, the protocol, the engine

The MCP server is a single new process that the engine already running today can be wrapped in. It speaks MCP upward to whatever AI client the user picked, and calls down into the existing PowerCodex internals.

The contract · what the AI can actually call

The tool catalog — the 7-stage loop as MCP verbs

Each lifecycle stage becomes one tool with a typed input schema and a structured result. Tools are deliberately coarse-grained (one stage = one call) so the AI orchestrates the order while PowerCodex owns the execution. Destructive tools declare a destructiveHint annotation and route through the consent broker before doing anything.

ToolStageWhat it doesGate
start_project0 · IntakeCaptures the goal + MVP, registers Approved_rights/, opens the dashboard, returns a session id.elicits rights
plan_change1 · PlanRuns the OpenSpec HTML workflow: Now→After, recommendation, questions batched once. Returns the spec artifact URI.safe
approve_change2 · ApproveRecords the human endorsement of a specific spec; unlocks build for that change only.elicits approval
build_assets3 · BuildEngine 1 drives the managed Edge browser to create Dataverse tables, columns, flows, connections — verified in-portal.destructive · gated
run_app4 · RunDecides power-apps push (Dataverse wired) vs npm run dev (local), returns the live app URL.push gated
test_app5 · TestEngine 2 runs e2e assertions against the approved MVP; returns pass/fail per screen + coverage.safe
self_heal5 · HealOn a real bug, drives opsx explore→propose→apply, re-runs, loops until green or cap hit.capped · may gate
observe6 · ObserveScans the running app for defects/gaps/improvements and drafts the next spec in the same HTML format.safe
get_statusanyReturns the live loop state — current stage, test counts, pending gates — same data the dashboard renders.safe

Why coarse tools beat fine tools here

If the AI had to call create_table, add_column, wire_relationship one at a time, every client would re-implement orchestration — and get it subtly wrong. By making build_assets the unit, PowerCodex keeps idempotency, verification, and rollback inside the engine. The AI decides what to build next, not how to click the portal.

Example: the build_assets tool definition

// Advertised in tools/list — the AI sees this schema and the safety hints
{
  "name": "build_assets",
  "title": "Build Power Platform assets from the approved spec",
  "description": "Creates Dataverse tables, columns, relationships, flows and connections in the maker portal, then re-reads the portal to verify each one. Requires an approved change.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "sessionId": { "type": "string" },
      "changeId":  { "type": "string", "description": "the approved change to build" }
    },
    "required": ["sessionId", "changeId"]
  },
  "annotations": {
    "destructiveHint": true,   // mutates the tenant — broker will elicit consent
    "idempotentHint": true,    // re-running converges, never duplicates
    "openWorldHint": true      // touches an external system (Power Platform)
  }
}

The other two MCP primitives

Resources to read, Prompts to reuse

Tools are verbs, but an AI also needs context to read and workflows to launch. PowerCodex exposes both so a fresh client can orient itself without the user re-explaining the project.

▤ Resources (read-only context)

  • powercodex://spec/{changeId} — the rendered HTML spec artifact + its markdown twin.
  • powercodex://status — live loop state JSON (stage, tests, gates).
  • powercodex://mvp — the approved MVP benchmark the app is tested against.
  • powercodex://tasks/{changeId} — the declarative task contracts Engine 1 will execute.
  • powercodex://learnings — the Learning_Experience/ digest the agent consults before planning.
  • powercodex://rights — the current Approved_rights/ grants (what the AI is allowed to do unattended).

Resources support resources/subscribe — the AI is notified when the spec or status changes, so it can react to a self-heal loop without polling.

⌘ Prompts (reusable workflows)

  • opsx:propose — draft a new change as an HTML spec artifact.
  • opsx:continue — resume an in-flight change.
  • opsx:apply — implement an approved change.
  • opsx:verify — check a change against its spec.
  • opsx:archive — close out a shipped change.
  • build-a-power-app — the full guided loop, end to end, for first-timers.

These appear in the client's prompt/slash-command picker. The user types /build-a-power-app in their own AI and the template injects the right system framing + tool sequence.

Sampling closes the loop

For steps that need model reasoning inside the engine (e.g. interpreting a goal, drafting a self-heal proposal), the server uses MCP sampling to ask the connected client's model to think — so PowerCodex needs no API key of its own. The user's AI does the reasoning; PowerCodex does the doing. One subscription, not two.

The non-negotiable part

How "bring your own AI" still can't skip your approval

The biggest risk of opening the loop to any client is that an over-eager agent fires build_assets or run_app push without a human in the loop. PowerCodex enforces the gate server-side, where no client prompt can override it, using MCP elicitation — the protocol's built-in mechanism for a server to pause and request structured input from the human.

⏸Elicitation, not trust

Every destructiveHint: true tool calls elicitation/create first. The client is required to surface it to the human and return accept/decline. A "yes" from the AI alone is never enough.

📁Approved_rights is the source of truth

If the user pre-granted build in Approved_rights/, the broker can auto-satisfy the gate — exactly the same rule the editor build follows. The folder, not the client, decides.

🚫Fails closed

If a client doesn't support elicitation, gated tools return a structured error pointing to the dashboard's manual-approve button. Default is always "don't act."

Threat model, stated plainly

Opening an MCP surface means untrusted prompts can reach the tool layer. Mitigations: (1) destructive tools always elicit; (2) the server validates that changeId was actually approved before build_assets runs; (3) HTTP transport requires OAuth with scoped tokens; (4) every tool call is logged to Learning_Experience/ with the originating session. The AI can propose anything; it can change nothing without a recorded human yes.

What the user actually does

Setup is one config block

For local use the client spawns PowerCodex over stdio. The user adds one entry to their client's MCP config and points it at a project folder. No servers to host, no keys to manage — the AI's own model does the reasoning via sampling.

Claude Desktop / Cursor / Cline — mcp.json

{
  "mcpServers": {
    "powercodex": {
      "command": "npx",
      "args": ["-y", "@voyager163/powercodex-mcp", "--root", "C:/work/projects-hub"],
      "env": { "POWERCODEX_DASHBOARD": "4321" }
    }
  }
}

Hosted / team — streamable HTTP with OAuth

{
  "mcpServers": {
    "powercodex": {
      "url": "https://powercodex.contoso.com/mcp",
      "transport": "http"
      // client runs the OAuth flow on first connect; tokens are scoped per project
    }
  }
}

The dashboard still opens

Whichever transport you use, start_project launches the same live dashboard on localhost:4321 (or the configured port). The user watches the loop there exactly as editor users do — the MCP route doesn't take the visibility away, it adds a second way to steer.

A real decision to make

Recommendation: ship local stdio first, hosted HTTP second

The two transports serve different users and carry very different risk. We don't have to choose forever — but we should choose what ships in v1.

Recommends

Ship the stdio (local, single-user) server first. It's the smallest surface, needs no auth infrastructure, matches how solo makers already run PowerCodex, and lets us harden the tool/consent contract before exposing it to a network. Add streamable HTTP + OAuth as a fast-follow once the tool catalog is proven.

v1 · Local stdio server ★ recommended first
  • No auth, no hosting — works the moment they add the config
  • Same trust boundary as running PowerCodex today
  • Fastest path to "drive it from Claude Desktop"
  • One user, one machine — no team sharing
v2 · Hosted streamable HTTP
  • One instance serves a whole team remotely
  • Centralised rights, audit, and learning log
  • Requires OAuth, token scoping, network hardening
  • Bigger attack surface — must land v1's gates first

How we get there

Four phases, each shippable on its own

Phase 1

Read-only server

Expose Resources + get_status + the opsx Prompts over stdio. No mutations. Any client can inspect a project. Proves the wiring.

lowest risk
Phase 2

Safe tools

Add start_project, plan_change, test_app, observe — everything that doesn't mutate the tenant. The AI can plan and test, not build.

plan + test
Phase 3

Gated mutations

Wire the consent broker and add approve_change, build_assets, run_app, self_heal. The full loop, locally, with elicitation enforced.

the real thing
Phase 4

Hosted & multi-user

Streamable HTTP transport, OAuth, scoped tokens, centralised audit. One PowerCodex serving a team of AIs.

scale out

Every phase is a real release

Phase 1 alone is useful — a maker can point Claude at an existing PowerCodex project and ask "what's the status, what's left?" We don't hold value back waiting for the full loop.
