Proposed change

Make the Canvas a real plan, not a checklist

Today the Canvas shows five vague checkboxes. This plan turns it into the same rich, illustrated document you get in docs/plans — with remarks, a capability breakdown, and Now vs After screenshots — and saves every one into the repo so the agent can refer back and learn.

Author: build assistant Scope: Canvas + planner + plan registry Date: 2026-06-08 Status: proposed

The gap today

What the Canvas shows vs. what you actually want

The Canvas you see in Chat is rendered by one small function. It never opens the rich plan document — it just lists the plan's plain-language items as checkboxes. The comprehensive plans you like are authored by hand and live somewhere else entirely; the build flow never produces one.

Specific to the request, illustrated, saved, and re-openable by the agent.

Root cause. renderCanvas() calls buildPreviewHtml(app.plan), which only knows plan.title and plan.items (the 3–6 strings from chat.js). The rich plan registry (plans.js → .powercodex/plans/) already exists and is already served, but nothing in the chat/agent flow ever authors or registers a rich plan HTML. Only the CLI stub and selftest write to it.

The shape of the fix

One generator, wired into the flow, saved to the repo

Add a single deterministic-first plan-document generator. The moment Chat produces a plan, the server authors a full HTML plan to .powercodex/plans/, registers it, and the Canvas renders that file instead of the checklist. Everything is reused: the registry, the server's path-guarded plan route, and the design language of docs/plans.

01

planhtml.js

New module. Turns goal + capabilities + the existing-screen digest into a self-contained HTML plan with remarks, a capability table, Now-vs-After mockups, build steps, and an outcome log.

02

Wire on plan

When chat.respond returns a plan, write & registerPlan it. The Canvas then loads the saved file via /api/plans — same path it already uses post-build.

03

Now vs After

Always-on deterministic mockups of the current screen vs the proposed one; upgraded to real Edge screenshots when the dev server + browser engine are live.

Reuse first. The generator emits the same CSS variables and component classes used by this document (.app, .shot, .callout, .pill). The mockup primitives mirror codegen.js's sample data so the picture matches the code that actually gets generated.

Anatomy of a generated plan

What every saved plan will contain

Each plan is one self-contained .html (no external assets) plus a sibling .json. The HTML is for you; the JSON is for the agent. Sections, in order:

SectionWhat it holdsSource
Header & summaryTitle, plan id (P00x), one-paragraph plain-language summary of the goal.plan.title, goal
RemarksShort rationale notes — why each choice was made, assumptions, what's sample data vs. real.capability flags + provider prose
Capability breakdownOne row per approved item: the plain capability, how it shows up on screen, and the concrete behaviour (e.g. "overdue → red").plan.items × parseCapabilities
Now vs AfterSide-by-side visuals of the current screen and the proposed one.digest + mockup/screenshot
Build · test · self-healThe ordered steps the loop will run, with the verify gate (tsc/build) called out.planTasks + verifyBuild
Task listThe concrete files that will be written/edited (e.g. src/pages/<kebab>.tsx, router wiring).planTasks
Outcome logFilled in after the build: created? routed? build passed? errors. This is what makes plans learnable.build results → re-render
Two artifacts, one plan. The .html is the human view; the .json is the structured record (goal, capabilities, tasks, outcome). The agent reads the JSON to learn from past plans without parsing HTML.

The visuals you asked for

"Now vs After" — two tiers, always something

The plan should never show a blank where a picture belongs. So there are two tiers: a deterministic mockup that always renders, and real screenshots when the environment can produce them.

🎨

Tier 1 — Deterministic mockup always

Rendered from the same capability flags and sample data codegen.js uses. "Now" reflects the existing screen from the digest (or "no screen yet"); "After" shows the proposed list/form with the behaviours applied — sorted, filtered, overdue rows in red. Pure HTML, no browser needed.

📸

Tier 2 — Real screenshots when live

When the project's dev server is running and the Edge/MDM browser engine is available, capture an actual screenshot of the current route ("Now") and, after the build verifies, the new route ("After"). Saved as .powercodex/plans/shots/<id>-{now,after}.png and embedded. Falls back to Tier 1 silently if unavailable.

Why a fallback matters. Screenshots need a running app and the browser engine — not guaranteed in every session. The deterministic mockup guarantees the plan always looks complete, and screenshots replace it opportunistically. The plan records which tier it used (visuals: "mockup" | "screenshot") so the agent knows how literal the picture is.

Saved so the agent can learn

Every plan lands in the repo

The registry already writes to .powercodex/plans/ and the server already serves it (path-traversal guarded). We extend the layout so each plan is a durable, self-describing record the agent can re-open, diff, and learn from.

The learning loop

  1. Plan is authored the instant Chat returns a plan — written + registered before the build starts.
  2. Build runs against that plan; buildCodeTasks + verifyBuild produce honest results (created / routed / build passed / errors).
  3. Outcome is folded back into plan-007.json and the registry entry, and the plan HTML's "Outcome log" section is re-rendered.
  4. Next time the planner reads recent plan-*.json to bias choices — reuse a screen that already exists, avoid a capability that previously failed to verify.
Definition of "learnable". A past plan is useful to the agent only if it pairs intent with outcome. Storing the goal + capabilities + the real build result (not just the request) is what lets the next plan be better than the last.
Decision needed: should .powercodex/plans/ be committed (so plans travel with the repo and teammates/the agent learn across machines) or git-ignored (local history only)? Recommended: commit the .html + .json, git-ignore shots/*.png to keep the repo light. Note .gitignore is already modified on this branch.

Implementation

Build steps, in order

Smallest path to value first: a richer Canvas you can see, then screenshots, then the learning loop. Each step is independently shippable.

  1. Create tools/lifecycle/lib/planhtml.js — exports renderPlanHtml({ goal, plan, capabilities, digest, outcome }) and renderPlanJson(...). Deterministic-first; reuses parseCapabilities/nameFrom from planner.js and the sample data shape from codegen.js.
  2. Author on plan — in the chat/intake server path, after a plan is produced, call renderPlanHtml, write .powercodex/plans/plan-N.html + .json, then registerPlan. Return the plan's file in the API response.
  3. Swap the Canvas source — in chat.html, point renderCanvas() at the saved plan file (it already loads /api/plans in refreshCanvas()). Demote buildPreviewHtml to a loading skeleton shown only until the file exists.
  4. Extend the registry — add outcome + visuals + jsonFile fields to registerPlan in plans.js, plus an updatePlanOutcome(root, id, outcome) helper.
  5. Fold outcomes back — after buildCodeTasks/verifyBuild in the loop, call updatePlanOutcome and re-render the HTML's outcome section.
  6. Tier-2 screenshots — add an optional capture using the existing Edge/MDM browser engine (engine/mdm-attach.mjs); guard behind "dev server reachable", fall back to mockup.
  7. Planner reads history — have planTasks glob recent plan-*.json and pass prior outcomes into capability selection.
  8. Mirror into the template — copy every change to templates/starter/tools/lifecycle/... so freshly scaffolded projects get it too.
Mirror the tree. This repo keeps a live copy under tools/lifecycle and a scaffolding copy under templates/starter/tools/lifecycle. Every file added or edited above must be applied in both places, or new projects ship the old checklist.

Guardrails

Risks & how we keep it honest

  • No theater. The mockup is labelled a preview; the outcome log shows the real build result. A plan never claims success the build didn't earn.
  • Self-contained HTML. Plans inline all CSS — no external assets — so they open from disk forever, even outside the server.
  • Path safety. Plans stay under .powercodex/plans/; the server route is already traversal-guarded. Screenshots write only into plans/shots/.
  • Graceful degradation. No provider → deterministic plan. No dev server → mockup instead of screenshot. Nothing in the chain can block a plan from appearing.
  • Backward compatible. The registry gains optional fields; existing entries and the post-build refreshCanvas() path keep working.

Definition of done

  • Sending a message in Chat produces a comprehensive plan in the Canvas — remarks, capability table, Now-vs-After — within one render.
  • A matching plan-N.html + plan-N.json exist on disk and appear in index.json.
  • After a build, the plan's outcome log reflects the true created/routed/verified result.
  • The same behaviour ships in a freshly scaffolded project from the starter template.
