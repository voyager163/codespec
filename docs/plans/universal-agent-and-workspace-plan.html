From a plan-only chat to a real, universal build agent.

PowerCodex should recognise what you actually want — a quick answer, an architecture overview, a build plan, or hands-on work — and act on it. PowerApps-first, but never PowerApps-only. What's actually broken

Diagnosis — grounded in the code

Five issues, each traced to a specific place in the shipped app. This is the honest starting point; every workstream below maps back to one of these.

1
Agent mode is a no-op. Typing a message while "Agent" is selected silently flips back to Chat and routes through the normal chat handler — the agent never does anything. The Agent button only reacts when a plan already exists; otherwise it prints a canned line. The single real execution path (build()) is wired exclusively to the hard-coded PowerApps lifecycle loop.
assets/chat.html · onSend() L562–568 (if(app.mode==='agent') setMode('chat')) · modeAgent.onclick L573 · build() L379
2
The chat is hard-wired to only ever produce a plan. The system prompt forbids any answer that isn't a friendly 2–4 sentence blurb plus a <<<PLAN…>>> block, and the offline brain always synthesises a build plan — even when you asked a question. "Give me an architecture overview" comes back as a tiny blurb plus an irrelevant build card. There is no intent detection at all.
lib/chat.js · SYSTEM L9–21 · heuristicPlan always-on L88 · history capped to 12 turns L25
3
Everything downstream assumes one shape: a PowerApps screen over a table. Capability flags (filterByUser, sort, highlight, search, rowAction) and tasks (code.screen / dataverse.*) are the only vocabulary. There is no representation for a Power BI dashboard, an architecture document, or any other artifact — and no MCP routing anywhere (a repo-wide search for "mcp" returns nothing).
lib/planner.js · lib/planhtml.js (SAMPLE rows, "Now vs After") · lib/codegen.js
4
It doesn't learn as the conversation progresses. The provider sees only the last 12 chat turns. Build outcomes are folded back into individual plan documents, but nothing accumulates project-level memory — goals, decisions, preferences, what's been built — that the assistant re-reads on every turn.
lib/chat.js buildPrompt L25 · lib/planhtml.js foldOutcome (per-plan only)
5
No workspace file tree, and the canvas can't be resized. The folder browser returns directory names only — never files. The canvas is a fixed-width toggle drawer (width:min(46%,560px)) with no drag-to-resize and no way to give the preview more room.
lib/browse.js (dirs only) · assets/chat.html .canvas L171–172 (fixed width, toggle only)
Compounding factor. The desktop shell boots the server with simulate:false (desktop/main.js L31). The real engine only does real work for a code-app or a browser project; a just-created workspace whose dependencies are still installing fails the build gate — so even the one path that "works" frequently looks broken. Honest status messaging is part of the fix.

Where this goes

PowerCodex as a universal build companion

One window that can chat, answer, plan, and act — and is smart enough to tell the difference on its own. PowerApps remains the flagship path (scaffold → code → test → deploy), but the same surface drives any project: a Power BI dashboard, an architecture write-up, a static site, or plain Q&A.

🧭
PRINCIPLE 01

Intent-first

The assistant classifies each turn before it answers. A question gets an answer; a build request gets a plan; "do it" runs the agent. No forced plan cards.

🧱

Artifact-agnostic canvas

The canvas renders whatever the AI authored — a plan, an architecture doc, a Power BI dashboard HTML, a diagram — not just the one PowerApps plan template.

Right tool per project

How we build it

Six workstreams

Each is independently shippable and maps to a diagnosis above. All changes live under tools/lifecycle (the engine the desktop app vendors at build time); no new runtime dependencies are required.

WS 1Make Agent mode realfixes #1

Turn the dead toggle into a genuine mode. Chat converses and proposes; Agent executes against the active workspace and streams progress. Decouple "Agent" from the PowerApps-only build() path.

Client (assets/chat.html)

  • Remove the if(app.mode==='agent') setMode('chat') bounce in onSend(); route to handleAgent() when in Agent mode.
  • Agent send posts to a new POST /api/agent with the message, history, active provider and a chosen objective (build / edit / run / explain-in-repo).
  • Render a live run/activity card (reuse the existing .run + tool-stream styling) fed by the bus, not the canned 7-stage strip.
  • Keep the permission toggles (Build / Auto-fix / Publish) as the agent's guardrails.

Server (lib/agent.js — new)

  • A general agent runner that drives the resolved provider (Claude Code CLI when present) with the workspace as context, streaming tokens + onTool events onto the bus.
  • For PowerApps build objectives it delegates to the existing controller (intake+start) so nothing regresses.
  • For everything else it runs a bounded, tool-using session and writes results as artifacts (WS3).
  • Honest degradation: when no real CLI is present, say so plainly and fall back to the simulated brain — never pretend.
The provider bridge already streams tool activity (lib/providers/_cli.js detectTool) — Agent mode surfaces those events instead of throwing them away.
WS 2The smart intent routerfixes #2

Before answering, classify the turn. This is the "is this a plan or not?" intelligence the app is missing.

"Give me an architecture overview of this app"
💬Chat

Open-ended talk. Reply normally, no card.

📐Answer / Artifact

"Architecture overview", "explain", "compare" → author a document & show it in the canvas.

📋Plan

"Build me a screen that…" → the plan card (today's behaviour), kept intact.

⚡Act

"Do it" / "fix it" / "deploy" → hand to Agent mode (WS1).

Implementation (lib/chat.js)

  • Replace the single plan-forcing SYSTEM with a router prompt that returns an intent + the response. Provider-led when a CLI is present; a deterministic keyword classifier as the offline fallback.
  • Only attach a plan when intent==='plan'. Stop the unconditional heuristicPlan().
  • Add intents: chat, answer, plan, act, artifact.

Behaviour the maker feels

  • Questions get real answers — including technical ones, since the "no jargon ever" rule is relaxed for answer intents.
  • The plan card stops showing up uninvited.
  • The canvas opens automatically when an artifact is produced.
WS 3A canvas that renders any artifactfixes #3

Generalise the plan-document generator into an artifact system. The plan HTML stays as one artifact type; new types share the same save/register/render path so the canvas can show them all.

New: lib/artifacts.js

  • A registry of artifact types — each is { id, kind, title, file, createdAt } saved under .powercodex/artifacts/ alongside today's .powercodex/plans/.
  • Renderers per kind: plan (existing planhtml.js), architecture, powerbi-dashboard, document, diagram.
  • Generic free-form HTML capture: when the agent authors an HTML file, register it as an artifact so the canvas renders it.

Server + client

  • GET /api/artifacts lists them; the existing .powercodex/plans/ file-server route is widened to also serve .powercodex/artifacts/ (same path-traversal guard).
  • The canvas iframe already renders any saved HTML by URL — point it at the artifact file (today's refreshCanvas() generalises cleanly).
  • A small artifact switcher in the canvas header to flip between recent artifacts.
"Architecture overview" worked example. Router → artifact: architecture. The agent reads the repo digest (lib/digest.js already exists), authors an architecture HTML (components, routes, data flow, engines, deploy path), saves it as an artifact, and the canvas opens it — exactly the kind of overview you'd expect.
WS 4Project-type detection & MCP routingfixes #3

Let the workspace decide which capabilities engage — and bring in the Power BI MCP for BI work, while staying graceful when a server isn't there.

Detection (extend lib/engines.js)

  • Today it detects code app + browser project. Add detectors for Power BI (.pbix / .pbip / TMDL), generic web, and docs/empty.
  • Surface the detected type in /api/state.project so the chat header can show it ("Power BI project", "Code app").

MCP bridge (lib/mcp.js — new)

  • Read MCP server definitions from the workspace's .vscode/mcp.json (where VS Code keeps them) and expose available servers to the agent.
  • When a Power BI project is detected and a Power BI MCP is configured, the agent can call it for dataset / dashboard tasks.
  • Optional & safe: no MCP configured → the agent authors a standalone Power BI dashboard HTML artifact instead. Never a hard dependency.
This is the "create a Power BI dashboard HTML using the Power BI MCP" path you described: detect Power BI → prefer the MCP if present → otherwise produce a real HTML artifact you can use immediately.
WS 5Conversation memory & learningfixes #4

New: lib/memory.js

  • A durable, append-friendly project memory at .powercodex/memory.json: goals, decisions, preferences, artifacts built, open questions.
  • Updated after each turn and each build outcome (extends what foldOutcome already does, but project-wide).
  • Summarised into a compact "what we know so far" block injected into every prompt — so context survives past the 12-turn window.

Wired into

  • lib/chat.js buildPrompt() — prepend the memory summary above the recent turns.
  • lib/agent.js — the agent reads memory before acting and writes decisions back.
  • A "Memory" view in the status panel so the maker can see (and correct) what PowerCodex believes.
Honest learning. Memory is plain JSON in the workspace, fully inspectable and editable — the assistant gets smarter without anything opaque happening behind the maker's back.

Sequencing

Phasing

Ordered so the most painful, most visible problems land first and each phase is usable on its own.

Phase 1 · Make it respond like a brain

Intent router + relax the plan-only prompt (WS2)

Smallest change with the biggest felt difference: questions get answers, the architecture overview works, and plan cards stop appearing uninvited. No new surfaces — just chat.js.

Phase 2 · Make Agent mode do something

Real Agent runner + live activity (WS1)

The toggle becomes a true mode. /api/agent + lib/agent.js, reusing the bus and tool-stream the provider bridge already emits.

Phase 3 · Make the canvas universal

Artifacts + architecture renderer (WS3)

Generalise the plan generator; the canvas renders any saved artifact. The architecture overview becomes a first-class artifact type.

Phase 4 · Make the window a workspace

File tree + resizable panels (WS6)

See your files, click to preview, drag to resize. Pure UI/UX on top of one new read-only endpoint.

Phase 5 · Make it broader & smarter

Project-type detection, MCP routing, memory (WS4 + WS5)

Power BI (and other) projects light up the right capabilities; the Power BI MCP is used when present; durable memory makes every later turn sharper.

Keeping it honest

Risks & guardrails

Don't break the flagship path

The PowerApps plan→build→test→heal loop stays exactly as-is; Agent's "build" objective delegates to the same controller. New behaviour is additive.

Agent must never pretend

With no real CLI, Agent mode says so and falls back to the simulated brain — matching the project's existing "honest by default" stance.

MCP is optional

Power BI / other MCP routing is a best-effort enhancement. Missing server → author a standalone artifact instead. No hard dependency, ever.

File access stays scoped & read-mostly

The tree and artifact server keep the existing path-traversal guards and only serve inside the active workspace. Writes remain gated by the permission toggles.

Classifier can be wrong

Intent is a hint, not a cage: every reply offers a one-tap "actually, build this" / "just answer" correction, and the maker can always switch modes.

Memory must be inspectable

Plain JSON in the workspace, shown in a Memory view, editable by the maker — learning without a black box.

The one-line version

PowerCodex stops assuming, and starts understanding.

It tells a question from a build, answers either, acts when asked, renders whatever it makes, remembers the project, and finally feels like the workspace it always wanted to be — PowerApps-first, everything-else-capable.
