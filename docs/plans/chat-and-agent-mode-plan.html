For people who'd rather talk than type commands

Two modes.
One calm conversation.

A low-code maker should never see a terminal, a file tree, or a YAML file unless they ask. PowerCodex becomes a single friendly chat screen with one switch: Chat to think out loud and shape a plan, Agent to sit back while it builds, tests, and fixes itself until it's clean — then you just keep chatting to add more.

Chat = discuss & plan Agent = build, test, self-heal One thread, never resets Desktop app · web for remote

The whole product in one sentence

The chat is the app

Everything you built — the lifecycle loop, the consent gate, the engines, the plans — stays exactly as is underneath. We're not changing the engine. We're changing the only thing the maker touches: instead of a developer's terminal cockpit, they get a chat window with two clearly-labelled modes and almost nothing else to learn.

MODE 01
💬

Chat mode — think together

A normal conversation. The maker describes what they want; PowerCodex asks friendly questions, suggests ideas, and quietly shapes it into a plan card — a short visual checklist with a big “Build this” button. Nothing happens to the app yet.

MODE 02
⚡

Agent mode — sit back

Approving the plan flips the same thread into Agent mode. Now it executes the full loop — design → build → run → test → fix — showing a plain-language checklist, not logs. When tests fail it fixes itself and retries. It only stops to ask you something or to get permission.

The key move: these are not two screens or two apps. They are two postures of the same chat thread. The maker switches with one toggle next to where they type — and most of the time PowerCodex flips it for them at the right moment, so they barely notice it exists.

The recommendation

The simplest thing that still feels safe

You asked for the best and simplest way any user could pick this up. The risk with two modes is making the maker manage modes. My recommendation removes that burden: keep the toggle visible for trust and control, but let PowerCodex move it automatically at the obvious moments. Here are the three options I considered.

★ RecommendedA · Auto-switch with a visible toggle

Default to Chat. The instant a plan is approved (“Build this”), PowerCodex slides the toggle to Agent itself; when the build finishes it slides back to Chat. The toggle is always visible and tappable, so the maker can override — but they never have to think about modes to succeed.

Pros

  • Zero mode-management for the maker — it “just flows”
  • The visible, moving toggle teaches the model by showing it
  • Still fully overridable → control + trust
  • One screen, one thread, one concept to learn

Cons

  • Slightly more logic to decide when to auto-flip
  • Auto-movement must be obvious or it feels “magic”
OptionB · Manual toggle only

The maker flips Chat/Agent themselves every time, like a deliberate switch.

Pros

  • Dead simple to build
  • Totally predictable

Cons

  • Makers forget to switch → confusion
  • Pushes a “developer” mental model onto them
OptionC · No modes at all (auto-detect)

One chat; the AI silently decides when to talk vs build.

Pros

  • Absolute minimum to learn
  • Feels like magic when right

Cons

  • Scary — it might build when you only wanted to chat
  • No clear “nothing happens yet” safety line
Why A wins for this persona: a low-code maker needs a visible, trustworthy boundary between “we're just talking” and “you're changing my app.” The toggle is that boundary. Auto-moving it keeps the simplicity of option C while keeping the safety of option B.

The rules that keep it simple

1️⃣

One screen, one thread

Never make them navigate. Plans, progress, permissions all appear inline as chat cards.

2️⃣

Plain English only

No file paths, YAML, or jargon on the surface. “Built the list,” not edit TaskList.fx.yaml.

3️⃣

Plans, not prompts

Chat always lands on a visual checklist + one button, so approving is reading, not authoring.

🖼️

Preview, don't describe

Every plan renders live on a canvas beside the chat. The maker sees the actual HTML page, never “a file was created.”

4️⃣

Progress, not logs

A friendly checklist with ticks. Technical detail is one disclosure tap away for the curious.

5️⃣

Heal silently

Fix failed tests automatically; surface only a calm “found & fixed” note. Interrupt only for real decisions.

6️⃣

Permission as switches

The consent gate becomes three plain toggles. Publishing is off until the maker says so.

7️⃣

Always end with “what next?”

Every build closes by inviting the next idea — keeping the forever-loop alive without a restart.

↩️

Always reversible

Every change offers Undo. Safety to experiment is what makes a maker brave.

Before we build · answer once

Open questions, with a suggested answer each

Each has a clear position — all six are now decided, each with the reasoning shown so you can overrule any of them with full information.

1Should the Chat/Agent toggle auto-switch, or always be manual?
Suggested: auto-switch with a visible toggle (Option A). Flips to Agent on “Build this,” back to Chat when done; maker can override anytime.
2Where does this live — replace the terminal cockpit, or sit alongside it?
Suggested: sit alongside. Friendly chat is the default surface; “Open developer view” reveals the existing cockpit. Same engine under both.
3After a build, who decides when to publish (go live)?
Suggested: always the maker, via the Publish switch. Build & test & auto-fix can be on by default; publishing stays off until explicitly enabled.
4Should the maker be able to keep typing while the Agent works?
Suggested: yes, queued. New messages are collected and handled after the current step, with a small “1 queued” chip — never interrupts a running build.
5Desktop app, web app, or both? decided
Decided: desktop app first, with optional remote web access. The desktop app bundles the engine for a zero-terminal install; a “Remote access” toggle serves the same UI over the web when you want to connect from another device. See Getting started.
6When connecting to an existing project, environment or local folder first? decided
Decided: pick a local project folder. “Add existing” opens a folder picker, vendors the core into .powercodex/ behind that picker, and runs brownfield ingestion on what's there. (Power Platform environment import can come later.)

How we'd build it

Sequenced so each step is usable on its own

Nothing here touches the engine — it's all surface. Each phase is shippable and testable before the next begins.

  1. The chat shell + mode toggle

    One thread, the Chat/Agent toggle, message bubbles. Wire Chat to the existing planning step and Agent to the existing lifecycle loop. Default to Chat; no auto-switch yet.

  2. The plan card & “Build this”

    Render the planner's output as a visual checklist with a Build button. Approving runs the loop. This alone delivers the core promise.

  3. The canvas (HTML plan preview)

    Render the agent's generated preview.html inline on a canvas beside the chat, with “open in browser” and “Build this” actions — so the maker previews the real plan without leaving the conversation.

  4. Friendly progress + silent self-heal

    Translate the status-bus events into the plain-language checklist; collapse logs behind “Show details”; surface self-heal as a calm note instead of a failure.

  5. The status button

    Bind the top-of-window button to the live status bus and lifecycle stage; tapping opens the summary panel (stage strip, MVP coverage, open issues, last activity, quick actions).

  6. Permission switches

    Map Approved_rights/ to three plain toggles; gate publish behind the maker. Greyed actions explain which switch to flip.

  7. Auto-switch + the forever loop

    Auto-move the toggle on build/finish; after each build, end with “what next?” and route new ideas into a fresh change without re-running intake.

  8. Desktop app + effortless onboarding

    Package the engine into a one-click installer (Windows/Mac); add the welcome screen with “new app” / “add existing” (running brownfield ingestion behind a button, not a command); add the Remote access toggle that serves the same UI over the web.

  9. Developer escape hatch

    Add “Open developer view” to reveal the full terminal cockpit, so power users lose nothing.
