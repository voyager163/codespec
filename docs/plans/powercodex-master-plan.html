The whole thing in one paragraph

You give it a goal and an MVP. It plans, builds, runs, tests, fixes itself, and learns — and you watch all of it live.

PowerCodex scaffolds a Power Apps Code App and wraps it in a spec-driven loop. This document folds the five plans into one ordered pipeline — not parallel tracks. You seed it with a goal and an MVP; first it authors a reviewable HTML spec artifact (the planning workflow); once you approve that, then a managed-browser build executor creates the real Dataverse tables, flows and connections (build · Engine 1); then an e2e tester runs the app against your MVP and self-heals through OpenSpec until green (test · Engine 2); then an observer notices defects, gaps and improvements and writes the next spec itself; a live dashboard shows every agent working; and a Learning_Experience log makes the whole thing get better over time (Hermes discipline). Every dangerous action is gated by Approved_rights/.

1First — Plan

The HTML-first OpenSpec workflow authors the spec: Now→After, a stated recommendation with pros/cons, all questions asked once, the "I am completely ready" sign-off. Nothing builds until this is approved.

2Then — Build & test

Only after the plan is approved: two engines on a managed Edge browser build the real assets in the maker portal, then test & self-heal the app via opsx until it matches the MVP.

3Then — Observe & loop

The observer authors the next spec from what it sees; the live dashboard renders it all; the learning log compounds the lessons — handing back to step 1.

One sequence, not two plans

"Planning" and "build & test" aren't separate or simultaneous tracks. Planning always comes first and must be approved; the build-and-test automation only runs on an approved spec. The seven steps below are that single order, start to finish.

The full end-to-end workflow

Seven steps, start to finish

This is the merged lifecycle — every plan in sequence. Each step hands its output to the next; the only deliberate stop is "green and matches the approved MVP."

0

Intake & the rights gate

Project start auto-opens the live dashboard, which collects two inputs and refuses to build without both: a goal (from your meeting summary) and an MVP (paste your prototype, or have one proposed and refine it). At the same moment it captures Approved_rights/ — your browser profile and whether the agent may run build / push on its own. That folder is re-read before every build, push, or browser launch.

goal + MVPApproved_rights/gate locked until compliant
1

Plan — the HTML spec artifact (Plan A)

Instead of drip-feeding markdown questions, the workflow renders a self-contained HTML artifact and opens it: a Now→After comparison, a stated recommendation with pros & cons, every open question batched once, a suggested proposal you edit rather than author, and — only when truly nothing is left — the line "I am completely ready, I have no more questions to ask." Built with the /emil-design-eng pass.

preview.htmlrecommend + pros/consready signal
2

Approve

You endorse the artifact in chat. The approved HTML + its markdown twin (OpenSpec tooling reads markdown) become the single source of truth both engines build and test against.

3

Build — Engine 1, the build executor (Plan B)

The codeapps skills (Dataverse, connectors, ALM) decide what assets are needed and emit declarative task contracts (small JSON). The build executor drives a managed Edge browser in the maker portal to create Dataverse tables, columns, relationships, flows and connections — then re-reads the portal to verify each one before reporting success. Idempotent, traceable back to the spec.

make.powerapps.comtask contractsverified in portal
4

Run — push, don't dev (once Dataverse is wired)

How the app is launched is decided per run: Dataverse connected → npx power-apps push and test the returned app link (local Vite can't resolve tenant data); no Dataverse → npm run dev on 127.0.0.1:5173 is fine. Push is gated by Approved_rights/.

power-apps push → app linkor npm run dev
5

Test — Engine 2, the self-healing loop (Plan B)

The same runtime tests the live app, every approved screen an assertion. Green & full MVP coverage → stop. On a real bug it doesn't just report — it drives opsx:explore → opsx:propose → opsx:apply, scaffolding a fix change, implementing it, re-running, and looping until green. Guardrails (iteration caps, a no-progress detector) keep "never-ending" safe.

e2e vs MVPself-heal via opsxcapped & escalating
6

Observe → Re-spec (lifecycle loop)

The observer watches the running app for three signals — defects, coverage gaps, improvements — and any one can mint the next change, rendered in Plan A's exact HTML format. It notifies you on the dashboard and in chat. Defects can auto-apply (if you allowed it); gaps and improvements wait for your endorsement. Then it loops back to Step 1. Every rotation is captured in Learning_Experience/ so the system stops repeating mistakes.

defect · gap · improvementnotifies youlearns

The Hermes discipline · why it compounds

It gets better over time, not just done once

Borrowed from Nous Research's Hermes Agent: the value isn't which chat app it plugs into, it's that it never stops learning. PowerCodex's medium is files in a reviewable repo — a better substrate for durable learning than an opaque session store. Every rotation writes a lesson; a reflection step scores the change; recurring patterns graduate into agent-drafted skills (gated by your review). The one number worth watching is the mistakes-per-change curve bending down.

✷Learn from mistakes

Learning_Experience/ is read at the start of every session and appended on every mistake — file-based, version-controlled. live today

↺Reflect

After apply/verify, a lightweight reflection records what worked, what was reworked, and any new lesson — the data the rest feeds on.

▰Recall & skill-up

Archived changes + lessons become a searchable digest the agent consults before planning; recurring wins become draft skills you approve.

Putting it together · a typical day

Four moves, and the loop does the rest

1

Start & seed

Run the project. The dashboard opens; you confirm the auto-filled goal and paste (or refine) the MVP. Set your Approved_rights/ once. Hit Verify & start build.

2

Plan & approve

In chat you say what you want; it returns the HTML artifact. You skim Now→After, accept or overrule the recommendation, answer the batched questions, and endorse.

3

Watch it work

Engine 1 builds the Dataverse assets, the app pushes, Engine 2 tests against your MVP and self-heals reds. You watch the agents move on the dashboard — no guessing.

4

Review what it found

The observer pings you with a new spec card (a gap or improvement). You open its preview.html, endorse or refine, and the next rotation begins. The Insights curve bends down.

Who's working

The agents in the loop

AgentOwnsWrites to the status bus
PlannerPlan A — authors/updates the HTML change artifact, batches questionsplan progress, open-question count, ready signal
Build executorEngine 1 — runs task contracts in the maker portal via MDM browserper-task status, screenshots, verified-in-portal
E2E testerEngine 2 — runs specs against the live app, drives self-healpass/fail per spec, MVP coverage %, loop iteration
Observer / spec authorWatches the run, classifies signals, mints new HTML specsnew observations, confidence, needs-approval flags
Dashboard writerRe-renders the live HTML pages from the busnothing — it only reads & renders

They never block each other

Agents communicate only through an append-only event bus and the file system (task contracts, results, observations). No agent waits on another's memory — so the build executor can be mid-task while the planner drafts the next change and the dashboard reflects both at once.

So "autonomous" stays safe

Guardrails on the loop

🛑No-progress detector

Same failure twice with no spec change → stop and escalate to you. Relentless, not reckless.

🔢Iteration & attempt caps

Per-iteration cap and max-attempts-per-failure stop runaway loops before they burn the tenant or your time.

🔐Rights-gated autonomy

Build, push, profile launch, autonomous re-spec and auto-apply are each separate Approved_rights/ flags, re-read every run.

🔔Notify before, not after

Gap/improvement specs surface as a proposal you approve. Only defect fixes — if you allowed it — apply unattended.

Goal-compliance is continuous

Every time the MVP changes — your refinements, the agent's proposals, or specs authored from observation — it is re-validated against the goal. If it starts drifting from what you set out to build, the loop stops and clarifies with you rather than quietly steering off-course.

What gets built · the system as files

One repo, five concerns, all reviewable

│ └── changes/<name>/preview.html # HTML artifact + proposal.md + tasks.md
├── automation/ # the two engines (Plan B)
│ ├── shared/ # managed-Edge bootstrap, auth, portal selectors, rights gate
│ ├── build-executor/ # Engine 1 — task contracts → portal actions → results
│ └── e2e-suite/ # Engine 2 — MVP-mirrored specs + self-heal orchestrator
├── .powercodex/live/ # the live dashboard (lifecycle loop)
│ ├── status.json # append-only event bus
│ ├── index.html # always-on dashboard + intake gate
│ └── stages/ · agents/ · observations/ # per-stage / per-agent / rendered specs
├── Approved_rights/ # consent gate — profile, build?, push?, auto-apply?
├── Learning_Experience/ # the learning loop (Hermes discipline) · live today
└── src/ # the React + Vite Power Apps Code App itself

Dog-fooded

Each of these capabilities is itself captured as an OpenSpec change first — authored as a Plan A HTML artifact, built and verified through Plan B. The system bootstraps itself.

The takeaway

A reviewable repo that plans, builds, tests, heals — and learns

The five plans were never really separate. Plan A produces the spec; Plan B consumes it to build and verify; the observer turns what it sees back into a spec; the dashboard makes all of it visible; and the learning loop makes every rotation cheaper than the last.
