Engineering Plan · MCP Hardening

Making the MCP server production-ready

A grounded, end-to-end plan to close the gaps between the current happy-path MCP prototype and a server safe to expose to Claude Code, Claude Desktop, Cursor, VS Code, and Antigravity. Harden the boundary, don't rewrite the engine.

Status: Proposed Scope: src/mcp/** + bin/powercodex-mcp.mjs Package: 0.2.0 · pre-release Priority: real (browser) mode 3 PRs · ~5–6 day pass

Decisions locked with the maker

Four answers that shaped this plan

These are product calls, not code calls — recorded here so the rationale travels with the plan.

1 Break freely

Pre-release, no external users. Tool return shapes and resource URIs can change cleanly with no compatibility shims. Simpler code, simpler review.

2 Broad host support

Claude Code, Claude Desktop, Cursor, VS Code, Antigravity. Claude Desktop's ~60s request timeout is the binding constraint — it forces the poll/resume gate redesign.

3 Deny outside workspace

Tools refuse paths outside the workspace root unless POWERCODEX_ALLOWED_ROOTS opts them in. Safest default; multi-repo users get an explicit escape hatch.

4 Plan first

This document lands in docs/plans/ as a tracked artifact before any code, so the approach is reviewable and committed.

Scope-defining decision: real mode is the priority

"Production-ready" means the real loop — managed Edge/CDP + Playwright + pac auth against a tenant — not just the offline simulate path. This expands Phase 1 with browser-lifecycle cleanup (1.4) and pac-auth failure handling (1.5), and splits the test strategy into CI-safe unit/contract tests (simulate) plus manual integration tests that need a browser, Playwright, and a signed-in pac profile and therefore can't run in CI. Effort grows from ~3–4 days to ~5–6.

What's actually wrong

The gaps, grounded in the code

The architecture is clean: server.mjs is a pure wiring point and every tool is a thin wrapper over tools/lifecycle/lib/*. The risk is concentrated entirely at the MCP boundary.

! Silent death

No try/catch around server.connect, no process error handlers, no graceful shutdown. An unhandled throw closes the pipe with zero diagnostic — and orphans the loop's Edge/CDP browser.

! Inconsistent errors

Most tool handlers await lib calls bare. A throw becomes a JSON-RPC protocol error instead of isError: true, so the model can't see or recover from the failure.

! Unconfined FS / exec

Every tool takes an arbitrary absolute path and reads, mkdirSync-writes, or spawns a process there. Effectively arbitrary filesystem-write + process-exec.

~ Long runs, no signal

The loop runs up to 20 rotations and only returns at the end. The rich emit stream is discarded until completion — and the run blows past host timeouts.

~ Broken approval gate

Hosts serialize tool calls and time out long requests, so approve_fix can never reach the server while start_lifecycle_loop is pending. The gate is unreachable in practice.

~ State & polish

Resources ignore per-call root; prompts are read once and frozen; server version is hardcoded; no MCP tests at all.

Correction from reading the engine

The approval gate is not an event-loop deadlock. waitForApproval in loop.js polls with await sleep(200), so it yields continuously. The real failure is one layer up: hosts won't dispatch a second tool call until the first returns, and they kill the first at ~60s. That reframes the fix from "make it thread-safe" to "don't model a human pause as one blocking request."

Phase 0 — Resilience & safety

The three blockers, with justification

0.1

Entry-point error boundary & graceful shutdown

What: wrap server.connect in try/catch logging to stderr; add uncaughtException, unhandledRejection, and SIGINT/SIGTERM handlers that close the transport and flush before exit.

Why: On stdio, stdout is the JSON-RPC channel — an unhandled throw kills the process and the host just sees the pipe close. A boundary turns "server vanished" into a logged, debuggable failure, and graceful shutdown runs eng.close() so a mid-flight loop doesn't orphan the browser.

resiliencebin/powercodex-mcp.mjs
0.2

Uniform tool error contract

What: one safeTool(handler) helper that catches throws and returns { isError: true, content: [...] }. Apply to every tool — including the pac tools, whose checkPac() throws.

Why: A bare throw becomes a transport error the model can't interpret or retry around. isError: true is the MCP convention precisely so the model reads the failure and self-corrects. One helper guarantees consistency instead of per-tool drift (today only two of six tools handle this).

error contractsrc/mcp/tools/*
0.3

Path confinement & input validation

What: a single resolveProjectDir(input, defaultRoot) that resolves to absolute, rejects paths outside an allow-list (default: workspace root; override: POWERCODEX_ALLOWED_ROOTS), and verifies existence for read tools. Route every path param through it.

Why: A host exposing these tools to a model otherwise grants arbitrary filesystem-write + process-exec. Confinement is the line between "automates my project" and "automates any path on the machine." Deny-by-default is least-surprise for a project tool; the env var keeps legitimate multi-repo use working.

Phase 1 — Long-running operations & real mode

From "works in a demo" to "works against a tenant"

With real mode as the priority, this phase carries the bulk of the effort: progress + timeouts (1.1–1.2), the gate redesign (1.3), and two real-mode hardening steps (1.4–1.5) that the simulate path never exercises.

1.1

Progress notifications for long tools

What: thread the request's progressToken into the existing emit callback so each loop/schema event becomes an MCP notifications/progress.

Why: The lib already emits a rich event stream we currently throw away until completion. Surfacing it keeps the user informed and keeps the request alive against idle-timeout heuristics. Low effort, high payoff — the seam already exists.

UXtimeouts
1.2

Bound long tools & make timeouts explicit

What: a maxDurationMs wall-clock cap on the loop and schema-apply tools; on breach, stop cleanly and return a partial summary marked stopped: true.

Why: Even with progress, a 20-rotation real loop can exceed any host's tolerance. A documented, returnable cap converts an opaque host-side kill (which skips cleanup) into a clean, reported stop. Predictability over open-ended runs.

guardrail
1.3

Redesign the approval gate: poll/resume, not blocking

What: start_lifecycle_loop runs until it finishes or hits the diff gate, then returns { state: 'awaiting_approval', resumeToken }. get_lifecycle_state reports the pause; new approve_fix/reject_fix set the decision; the loop continues via resumeToken. State lives in the server; no single request spans the human pause.

Why: This is the corrected diagnosis. The gate isn't broken by event-loop blocking — it's broken because hosts serialize tool calls and time out long requests, so the approval call can never arrive in time. A request/return/resume protocol is the idiomatic MCP way to model human-in-the-loop. reject_fix is added because today you can only approve; the loop already supports the "not approved → stop" path internally.

core redesignsrc/mcp/tools/lifecycle.mjs
1.4

Real-mode browser lifecycle & cleanup

What: guarantee eng.close() (CDP release) runs on every exit path of a real run — normal completion, duration cap, error, and shutdown signal — via a single finally in the tool handler. Detect a dead/unreachable Edge/CDP session and surface it as a clear isError rather than hanging.

Why: Real mode drives a managed Edge profile over CDP. Today an error or host-timeout between launch and eng.close() (loop.js:316) leaks a browser process and can lock the profile directory, breaking the next run. This is the single most likely real-mode failure and is invisible in simulate.

real modecleanup
1.5

pac-auth & profile failure handling

What: before a real run or push, verify pac is reachable and an auth profile matches the target environment; on missing/expired auth, return an actionable isError (which pac command to run) instead of letting the deep call throw mid-loop. Validate the browser profile pointer in Approved_rights/ exists.

Why: The pac tools already detect some of this, but the loop's real path can reach a push with stale/absent auth and fail opaquely partway through. Front-loading the check turns a confusing mid-run failure into a precise, recoverable message — the difference between a usable tool and a frustrating one against a live tenant.

real modetools/lifecycle/lib/pac-init.js

Why this is its own PR

1.3 changes the start_lifecycle_loop contract — the largest behavioral change in the plan. Isolating it keeps the Phase 0 safety fixes from being held hostage to its review. Since we're pre-release, no compat shim is needed; the new contract simply replaces the old, documented in the MCP user guide.

Phase 2 — Consistency & correctness polish

The papercuts that bite in npx & multi-project

FixChangeWhy
2.1 Per-project resources
resources/state · plans		 Move from fixed defaultRoot to a ResourceTemplate that accepts the project, resolved through the same root logic as tools. Tools take a per-call projectDir but resources are hardwired. In npx / multi-project sessions the tools operate on project A while resources report project B — a silent mismatch. One root model removes the footgun.
2.2 Live prompts
prompts/opsx		 Read each prompt file inside the callback (not at registration); rescan the directory per list; emit prompts/list_changed on change. Content is readFileSync'd once at startup and closed over, so editing a workflow prompt has no effect until restart and new files never appear. Lazy reads make prompts reflect the working tree — the whole point of surfacing repo files.
2.3 Version from package.json
server.mjs		 Import the version instead of the literal '0.2.0'. A hardcoded version silently lies on the next release, and hosts surface server version for diagnostics. Single source of truth.
2.4 stdout hygiene
whole server		 A startup dev-guard that nothing writes to stdout outside the transport; audit wrapped libs; document the rule. A single stray console.log in any lib corrupts the JSON-RPC stream and breaks the session in a way that's miserable to debug. Cheap insurance for an invisible failure class.

Phase 3 — Tests & CI

The net that keeps Phase 0–2 fixed

There are currently zero MCP tests — which is exactly why these regressions were invisible. Because real mode is the priority, the strategy splits in two: a fast CI-safe suite (simulate, offline) plus a documented manual integration checklist that needs a browser, Playwright, and a signed-in pac profile.

CI Automated · simulate mode

  • Boot & discovery: in-memory transport; tools/list, resources/list, prompts/list return expected names.
  • Error contract (0.2): a forced throw in each tool yields isError: true, not a protocol error.
  • Confinement (0.3): resolveProjectDir rejects out-of-allow-list paths, accepts allow-listed ones.
  • Approval gate (1.3): loop returns awaiting_approval; approve_fix + resume completes; reject_fix stops.
  • Live prompts (2.2): a prompt edited after boot is reflected in the next read.
  • Wired into the existing GitHub workflow via npm test so it can't rot.

manual Integration · real mode

  • Cleanup (1.4): kill a real run mid-flight (and via duration cap) — confirm no orphaned Edge process and the profile dir unlocks for the next run.
  • Auth (1.5): run with pac absent, with no profile, and with an expired profile — each returns an actionable isError, not a mid-loop throw.
  • Progress (1.1): a multi-rotation real run streams notifications/progress visibly in the host before returning.
  • Documented as a checklist in the repo (can't run in CI: needs browser + tenant). Run before each release.

Rollout & risk

How it ships safely

PR slicing

  • PR 1 — Phase 0. Small, reviewable, independently shippable. The server is safe after it.
  • PR 2 — Phase 1. Gate redesign, long-run handling, and real-mode browser/auth hardening; the largest and riskiest change, reviewed alone.
  • PR 3 — Phase 2 + 3. Polish plus the test suite that locks everything in.

Risks & mitigations

  • Breaking contract changes (1.3 return shape, 2.1 URIs): acceptable — pre-release, documented in the user guide. No shim.
  • Host never issues the resume call: the loop's internal timeout still applies, degrading to a clean "not approved → stop," never a hang.
  • Confinement breaks multi-repo users: POWERCODEX_ALLOWED_ROOTS is the documented escape hatch.
Recommendation

Land PR 1 (Phase 0) first — it removes the only unsafe behaviors and is mechanical enough to review quickly. PR 2 is the real engineering work: the gate redesign plus real-mode browser/auth hardening, validated against a live tenant. Estimate: ~1 day P0, ~3–4 days P1 (real mode), small P2/P3 — a ~5–6 day pass.
