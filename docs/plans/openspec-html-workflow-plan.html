What this plan delivers

Seven changes, one experience

Each card maps directly to something you asked for. Together they turn the workflow's output from a wall of markdown questions into an interactive, modern surface you skim and decide from.

1

HTML output by default

Explore / new / propose stop asking in plain text. They render a self-contained HTML artifact in the workspace and open it — that becomes the conversation surface.

2

Now vs After screenshots

Any proposed change embeds a side-by-side "Now → After" comparison (screenshot, mock, or rendered preview) with a draggable slider so the delta is obvious at a glance.

3

/emil-design-eng is required

The template mandates a design-engineering pass on every UI artifact — custom easings, scale-on-press, stagger, reduced-motion — so output is lively and modern, never static.

4

Always recommends, with pros & cons

Even inside OpenSpec, the workflow states its own recommended path and lays out pros & cons for each option as visual cards — so you can judge fast.

5

One-shot questions

Instead of drip-feeding questions, it gathers every open concern and presents them together, once, in the HTML — answer the batch and move on.

6

Always a suggested proposal

Every exploration output includes a concrete suggested proposal in the HTML, so you're never staring at a blank page — you're approving or adjusting a draft.

7

A clear "ready" signal

When nothing is left to clarify, the artifact ends with the exact line: "I am completely ready, I have no more questions to ask."

How we'll build it

Rollout in four phases

  1. Shared HTML artifact convention

    Author the reusable skeleton (self-contained HTML, custom easings, clip-path Now/After slider, pros/cons cards, one-shot question block, ready badge, reduced-motion). One source the prompts point to.

  2. Rewrite the OPSX prompts

    Update explore / new / propose / continue / ff to emit that HTML, always include a suggested proposal, batch all questions, and require the /emil-design-eng pass before finishing.

  3. Wire the ready-state contract

    Define exactly when the artifact prints "I am completely ready, I have no more questions to ask." — only after all batched questions resolve and a proposal + Now/After are present.

  4. Sync, verify, document

    Mirror to live .github/prompts, update config.yaml rules, extend the verify script to assert HTML output, and note the new behavior in the README.

A · How should "screenshots" be produced? suggested: rendered HTML/mock, no live capture

B · Where do HTML artifacts live? suggested: openspec/changes/<name>/preview.html

Markdown stays canonical for version control; HTML is the generated review surface beside it. Agree, or should HTML be canonical?

C · Should the HTML pass keep the markdown artifacts too? suggested: yes, both

OpenSpec tooling reads markdown, so I'd keep generating it and add HTML on top — not replace it. Confirm this is acceptable.
