Non-negotiable · runs before everything

Step 0 — Intake & the Approved_rights/ gate

Before any project starts, I ask you for the key operating permissions first, write your answers to a local Approved_rights/ folder, and re-read that folder before every build, push, or browser launch. Consent is recorded, not assumed.

What I ask at intake

  • Browser profile — which MDM/Edge profile should the runtime use?
  • Build autonomy — may I run npm run build on my own?
  • Push autonomy — may I run npx power-apps push on my own?

What gets saved (and always re-checked)

// Approved_rights/approval.json
{
  "browserProfile": "<your answer>",
  "allowBuild": true,         // npm run build
  "allowPush": false,        // npx power-apps push
  "grantedBy": "user",
  "grantedAt": "2026-06-03"
}

The gate is enforced, not advisory

If Approved_rights/ is missing or a flag is false, the runtime stops and asks rather than running build/push or launching a profile. Both engines below honor this.

What I understood

The goal: automate the entire build lifecycle

PowerCodex today scaffolds a Power Apps Code App (React + Vite), wires an OpenSpec (opsx) spec-driven loop, and ships Code Apps skills (architect, scaffolder, connectors, Dataverse, env-vars, ALM). What's missing is a hands-on-keyboard runtime — something that can drive the real Power Platform maker portal and the running app through a managed browser. That is what the MDM-Playwright infrastructure adds, and you want it serving two distinct jobs.

🛠 Use case 1 — Build executor (cowork)

After planning, the app still needs things that can't be created from app code alone: Dataverse tables, columns, relationships, Power Automate flows, connections. The AI hands these as tasks; the MDM browser executes them in the maker portal on your behalf.

cowork make.powerapps.com Dataverse Power Automate

🧪 Use case 2 — E2E tester (self-healing)

The same runtime tests the built app end-to-end. When something breaks, its job isn't just to report — it's to open an OpenSpec change and drive explore → propose → apply until the fix lands. It loops until zero bugs and the app matches your MVP / approved HTML.

e2e opsx:explore opsx:propose opsx:apply

The hard rule you set: keep them in two separate folders

Building and testing must never get confused. So the runtime is split into two top-level folders with their own configs, their own browser profiles, and their own entry points — sharing only a small, common browser-bootstrap library.

🔒 Separate browser profiles

Build-executor uses an authenticated maker profile (can mutate your tenant). E2E uses an app-runtime profile (read/interact only). Different storageState files, never shared.

🧩 Shared bootstrap only

The only thing in common is shared/ — how to launch managed Edge and where selectors live. No test logic leaks into build logic or vice-versa.

The MDM browser

What "managed browser" means here

Power Platform sits behind tenant conditional-access / device-compliance. A throwaway headless Chromium often can't pass it. The MDM approach launches a real Microsoft Edge channel with a persistent user-data dir, performs login once, and reuses the saved session — so both engines act as a genuinely signed-in maker.

// automation/shared/mdm-browser.ts (shape — to be aligned to ElfredSeow's repo)
export async function launchMdmContext(profileDir: string, storageState?: string) {
  return chromium.launchPersistentContext(profileDir, {
    channel: "msedge",        // real managed Edge, not bundled Chromium
    headless: false,           // MDM/conditional-access often needs headed
    storageState,               // reuse the one-time login
    viewport: { width: 1440, height: 900 },
  })
}

Auth is a one-time, human-in-the-loop step

auth.setup.ts opens the portal, you complete MFA once, and the session is captured to storageState. Subsequent build/test runs are fully unattended until the session expires. No credentials are stored in the repo — only the gitignored state file.

Engine 1 · build executor

How the AI builds real assets through the browser

The codeapps skills (Dataverse, connectors, ALM) decide what is needed. They emit a task contract — a small JSON the build-executor knows how to perform. This keeps the AI's intent declarative and the browser automation deterministic.

Task contract (input)

// automation/build-executor/tasks/create-projects-table.task.json
{
  "type": "dataverse.table.create",
  "displayName": "Project",
  "schemaName": "cr123_project",
  "columns": [
    { "name": "Status", "type": "choice" },
    { "name": "DueDate", "type": "datetime" }
  ],
  "source": "example-dataverse-model"
}

Result (output)

// automation/build-executor/results/create-projects-table.json
{
  "status": "succeeded",
  "tableId": "cr123_project",
  "screenshots": ["results/shots/table.png"],
  "verifiedInPortal": true,
  "durationMs": 18422
}
  • Declarative in, verified out — every action re-reads the portal to confirm the asset exists before reporting success.
  • Idempotent — re-running a task that already succeeded is a no-op, so the loop can retry safely.
  • Traceable — each task links back to the OpenSpec capability (source) that requested it.

Engine 2 · the never-ending loop

Test → detect → self-heal via OpenSpec → retest

This is the heart of what you asked for. The e2e-suite doesn't just fail loudly — on a real bug it drives the opsx skills itself and won't stop until the app is green and matches your approved MVP/HTML.

1

Run e2e against the live app

Target resolved by Dataverse state: pushed power-apps app link (push gated by Approved_rights/) or local dev. Specs mirror the approved MVP/HTML — every approved screen and interaction is an assertion.

2

Green? → exit loop

If all specs pass and coverage of the MVP surface is complete, the loop terminates successfully. This is the only stop condition.

3

Red? → opsx:explore

Failure artifacts (trace, screenshot, DOM, console) feed an explore pass to understand the root cause — thinking only, no code yet.

4

opsx:propose a change

failure-to-change.ts scaffolds openspec/changes/<fix-…>/ with proposal + tasks + spec deltas describing the fix.

5

opsx:apply the change

Implement against the spec, run unit + lint + the failing spec, then archive the change when it validates.

6

↺ Back to step 1

Re-run the full suite. New regressions feed the loop again. Repeat until step 2 is reached.

Guardrails so "never-ending" stays safe

Per-iteration cap, max-attempts-per-failure, and a "no-progress" detector (same failure twice with no spec change → stop and escalate to you). The loop is relentless, not reckless.
