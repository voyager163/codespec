The link you asked me to find

Two plans, two halves of one circle

On their own, the two plans look separate — one redesigns how specs are presented, the other automates how the app is built and tested. But they share one object: the HTML spec artifact. Plan A produces it; Plan B consumes it to build and verify; and when Plan B observes something new, it produces another one — handing control straight back to Plan A. That handoff is the link, and it's what turns a one-way pipeline into a self-feeding loop.

Plan A · front of the pipe

HTML-first OpenSpec workflow

Authors a change as a living HTML artifact: Now→After, a stated recommendation with pros/cons, every question asked once, a suggested proposal, and the "I am completely ready" sign-off. This is the approved source of truth.

⟲
Plan B · execution + verification

Playwright-for-MDM automation

Engine 1 builds the real Dataverse tables / flows / connections through the managed browser. Engine 2 tests the running app against the approved MVP and self-heals via opsx until green.

The missing piece that closes it

Plan B already scaffolds an OpenSpec change on a failure. We make that scaffold come out in Plan A's exact HTML artifact format — and we widen the trigger from "a test failed" to "the observer noticed anything worth a spec." Now the e2e/observer engine is also a spec author, and the output of Plan B is a valid input to Plan A. The pipe becomes a wheel.

Step 0 · before a single line is built

Two inputs seed the whole loop — and nothing starts without them

The loop is only as good as what it's aimed at. So before the wheel turns, the dashboard collects two things and refuses to build until it has both. They become the loop's north star and its benchmark.

Input 1 · the north star

Summarised meeting transcript → goal & objective

You paste a summary of the meeting where the solution was discussed — what it's for, who uses it, what success looks like. This becomes the full user story + objective that every later decision is measured against. It is stored with the project and always kept in context, never discarded.

  • Always present — the goal travels with every spec, build task, and test.
  • The tie-breaker — when options conflict, the one closest to the stated objective wins.
Input 2 · the benchmark

An MVP — paste yours, or I propose one

Two ways in, your choice:

  • You have a prototype — paste the quick build you made in an external AI tool (Google AI Studio, v0, etc.) as a URL or HTML. I adopt it as-is.
  • You don't — I propose an HTML MVP showing what your product could look like, and you keep prompting me to refine it until it's right.
  • Either way it becomes the benchmark — the approved MVP is the target the entire app is built and tested against. Scaling happens after, from this baseline.

⚠ Continuous compliance: the MVP must always serve the goal

Every time the MVP changes — your refinements, my proposals, or specs authored from observation — I re-validate it against the meeting transcript / objective. If the MVP starts drifting away from what you originally set out to build, I stop and clarify with you rather than quietly steering off-course. You confirm the new direction (or correct it) before the build continues. The goal anchors the MVP; the MVP anchors the app.

Where this happens: the dashboard, not an IDE

Both inputs are collected right in the live dashboard, which opens automatically whenever you start a project. If you've already typed the goal or a prototype into chat, the dashboard auto-fills those fields so you just confirm — no jumping into an editor. The "Verify & start build" gate stays locked until both a goal/objective and an MVP are present and the MVP reads as compliant with the goal.

The heart of it · self-authored specs

It writes its own specs from what it sees — then tells you

The observer doesn't only react to red tests. As it drives the real app it watches for three classes of signal, and any one of them can mint a new change — rendered in the same HTML you already approve from.

🐞 Defects

A spec assertion fails, a console error fires, a screen drifts from the approved Now→After. Classic self-heal trigger.

🧭 Gaps

An approved MVP surface has no covering spec, a Dataverse field is referenced but never built, a flow is missing. Coverage holes become proposals.

✨ Improvements

A slow interaction, a clumsy empty-state, an accessibility miss. Lower-priority, but logged and offered — never silently applied.

What the observer emits

// openspec/changes/<auto-fix-table-drift>/observation.json
{
  "origin": "e2e-observer",
  "signal": "defect",        // defect | gap | improvement
  "evidence": ["trace.zip", "shots/drift.png"],
  "confidence": 0.86,
  "suggestedProposal": "Restore Status choice column…",
  "renderedArtifact": "preview.html",   // Plan A format
  "needsApproval": true
}

How you hear about it

  • Dashboard notification — a new card appears in the live "Specs authored from observation" panel the instant it's written.
  • Chat ping — a one-line summary with a link to the rendered preview.html.
  • Ready-gated — the artifact still ends with Plan A's "I am completely ready, I have no more questions to ask." only when it truly is.
  • Your call — defects can auto-apply (if you allowed it); gaps and improvements wait for endorsement.

Consent is inherited, not invented

Autonomy is bounded by the same Approved_rights/ gate from Plan B. "Author specs from observation" and "auto-apply defect fixes" are explicit flags. With them off, the loop still observes and drafts — it just stops at "here's a proposal, endorse it?" instead of applying.

Your second ask · the live view

Every stage — and every past stage — has a local HTML page that never stops updating

You should never have to guess what the agents are doing. So every stage writes its state to a structured status file, and a tiny writer re-renders self-contained HTML on every change. Open the dashboard once and watch the whole loop breathe.

How "live" works without a server

  • One status bus — each agent appends events to .powercodex/live/status.json (append-only, timestamped).
  • A writer re-renders — dashboard-writer watches the bus and rewrites the HTML pages on every event.
  • The page self-refreshes — the dashboard polls its own status file (or uses a file-watch live-reload) so it updates with no manual reload.
  • Past stages persist — each completed stage keeps its own frozen HTML page; nothing is overwritten, so history stays browsable.

They never block each other

Agents communicate only through the append-only bus and the file system (task contracts, results, observations). No agent waits on another's memory — so the build executor can be mid-task while the planner drafts the next change and the dashboard reflects both at once.

So "autonomous" stays safe

Guardrails on the loop

🛑 No-progress detector

Same failure twice with no spec change → stop and escalate to you. Relentless, not reckless.

🔢 Iteration & attempt caps

Per-iteration cap and max-attempts-per-failure stop runaway loops before they burn the tenant or your time.

🔐 Rights-gated autonomy

Build, push, profile launch, autonomous re-spec, and auto-apply are each separate Approved_rights/ flags, re-read every run.

🔔 Notify before, not after

Gap/improvement specs surface as a proposal you approve. Only defect fixes (if allowed) apply unattended.

Order of work

Four phases

1

The status bus + dashboard writer

Stand up .powercodex/live/, the append-only bus, and the writer that re-renders HTML on every event. Ship the live dashboard page (the demo becomes the template).

2

Wire every agent to emit

Planner, build executor, e2e, observer all call emit() at each meaningful step. Per-stage and per-agent pages start updating live.

3

The observation → Plan-A bridge

Teach Engine 2 to classify signals and render new HTML spec artifacts; OPSX prompts accept them. Notifications fire to dashboard + chat.

4

Close & gate the loop

Connect Node 6 back to Node 1 under Approved_rights/ flags. Add guardrails, verify with a real end-to-end rotation, document.

Decisions I'd lock before building

① Auto-apply scope

Should defect fixes apply unattended once trusted, while gaps/improvements always wait for you? I recommend yes — defects auto, the rest gated. suggested: yes

② Live-refresh mechanism

Self-polling the status file (zero deps) or a tiny live-reload watcher (snappier)? I recommend polling for portability. suggested: poll

③ Where live/ lives

.powercodex/live/ at repo root (gitignored) vs inside automation/. I recommend repo root so all agents share one view. suggested: repo root

④ Observation noise budget

A confidence threshold below which improvements are logged but not surfaced, to avoid notification spam? I recommend 0.6. suggested: 0.6
