PowerCodex — why it failed, and what it taught us

A plain-language post-mortem of the issues hit while turning PowerCodex into a real, sign-in-capable autonomous app builder — written so the next person (or the next you) doesn't lose a day to the same traps.

📅 8 June 2026 Author: build session handover Scope: desktop app · lifecycle engine · AI sign-in
TL;DR — Nothing was ever wrong with your Claude account; you were signed in the whole time. The app simply couldn't tell, because it checked sign-in the slowest, most fragile way possible (a full AI round-trip that timed out), and the “Sign in” button itself crashed on a Windows quoting bug. Separately, the product looked finished but was simulating the build instead of really creating an app. Each of those is a specific, avoidable mistake — captured below.

The failures, one by one

What went wrong & why

1“Windows cannot find PowerCodex” when clicking Sign inFixed
Symptom
Clicking Sign in to Claude Code popped a Windows error: “Windows cannot find PowerCodex. Make sure you typed the name correctly.”
Root cause
The app opened a terminal with start <title> cmd /k claude — but the window title was not quoted. Windows start only treats the first token as a title when it’s in quotes; unquoted, it read the first word — PowerCodex — as the program to launch.
Why it happened
A one-line shell command that “looked obviously correct” was never run on real Windows. start’s title-vs-command quoting rule is a classic footgun.
Fix
Quote the title and wrap the command: start "PowerCodex — sign in" cmd /k "claude", run through cmd /s /c so the quotes survive. Verified a real titled terminal now opens.
Lesson
A command that spawns a process is code — test it on the real OS, not by reading it. Windows start always needs a quoted title (even an empty "").
2The app kept insisting you weren’t signed in (when you were)Fixed
Symptom
Even with Claude installed and logged in, the “Connect your AI” gate kept reappearing and never registered you as connected.
Root cause
“Am I signed in?” was answered by sending a real prompt to the model and waiting for a reply. That took ~10 seconds against a 12-second timeout — so it routinely timed out and reported not signed in. The providers were also checked one after another, stacking the delay.
Why it happened
A comment claimed “there’s no stable way to check login,” so the code reached for the heaviest possible probe — one that costs time, tokens, and reliability on every recheck.
Fix
Read local auth state instead: Claude’s OAuth token in ~/.claude/.credentials.json (plus ANTHROPIC_API_KEY and the account marker in ~/.claude.json). Result: 95 ms and a correct true. Probes now run in parallel — full check dropped from ~10–24 s to ~0.6 s.
Lesson
Never test a cheap fact (is a token on disk?) with an expensive action (call the model). A health check must be fast, free, and deterministic — or it becomes the outage.
3It tried to make you sign in to Power Platform — to build locallyFixed
Symptom
A managed-Edge / Microsoft sign-in was triggered up front, even though you only wanted to build an app on your own machine and weren’t publishing anywhere.
Root cause
The loop eagerly “verified the browser profile” (which attaches to Edge for a Microsoft login) before doing anything — instead of only when a publish actually happens.
Fix
Sign-in is now deferred and publish-only. Building on-device requires no Microsoft account; Power Platform login happens lazily, and only if you choose to publish (gated by the Publish switch).
Lesson
Don’t demand credentials a task doesn’t need. Gate every sign-in behind the specific action that actually requires it — make the common, local path friction-free.
4“Missing script: build”Fixed
Symptom
npm run build failed with Missing script: "build".
Root cause
The desktop/ folder’s build command was named dist:installer, not build — three folders here each have different scripts, and the intuitive name wasn’t wired.
Fix
Added a build alias to desktop/package.json so the obvious command builds the installer.
Lesson
In a multi-package repo, make the obvious command work in each folder. “Which directory am I in?” is the first question to ask a confusing npm error.
5It looked finished, but it was simulating the buildFixed
Symptom
The UI showed a polished “Intake → Plan → Build → Test → Done” flow — but it created no actual app. The build engine only navigated to Power Platform and reported success it hadn’t earned.
Root cause
The lifecycle loop ran a scripted narrative (hardcoded tasks, a fake self-heal, a placeholder app URL). The real work — generating app code — didn’t exist.
Fix
Built the real spine: a planner (plan → concrete tasks), a code generator that authors real React/TypeScript screens and wires them into the router, a real build gate (the app’s own npm run build), and real self-heal. AI authoring is used when signed in; a deterministic template generator runs otherwise.
Lesson
A convincing demo is not a working product. “Simulated” must be loud, not silent — and the honest question for any agent is always: did a real artifact get created and verified?
6Couldn’t prove the generated app compiles (here)Environmental
Symptom
npm install / npm run build hung or failed with No matching version found for @babel/code-frame.
Root cause
The build sandbox had no working npm registry (network blocked). Not a code defect — the package manager simply couldn’t fetch dependencies.
Fix / mitigation
Proved correctness another way: the generated TypeScript was parsed and transpiled with the local compiler (valid TSX, strict mode), and the end-to-end loop was run in real mode. The final npm run build green-light must be confirmed on a networked machine.
Lesson
Know the difference between “my code is wrong” and “my environment is broken.” When a tool fails, read the actual error — and have a second, offline way to verify so a blocked network doesn’t masquerade as a bug.

The takeaways

Five lessons worth keeping

⚡

Health checks must be cheap

Detect state from local facts (a file, an env var), never by performing the expensive action you’re checking for.

🪟

Shell commands are code

Quoting, titles and && behave differently per OS. Run them on the real platform — don’t eyeball them.

🔐

Ask for sign-in only when needed

Gate each credential behind the exact action that requires it. Keep the local, common path account-free.

🎭

Simulated ≠ done

A pretty flow can hide an empty engine. Always ask: was a real artifact created and verified?

🌐

Separate bug from environment

“Can’t install” is often the network, not the code. Read the real error; keep an offline check in reserve.

🧭

Know which folder you’re in

Monorepos have many package.json files. Make the obvious command work everywhere.
